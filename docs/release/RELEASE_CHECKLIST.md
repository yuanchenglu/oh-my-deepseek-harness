# Release Checklist

- Status: Execution checklist; no Gate is implied complete by this file
- Normative plan: [`OPEN_SOURCE_RELEASE_PLAN.md`](../roadmap/OPEN_SOURCE_RELEASE_PLAN.md)
- Security policy: [`SECURITY.md`](../../SECURITY.md)
- Test plan: [`TEST_PLAN.md`](../testing/TEST_PLAN.md)
- Traceability: [`RELEASE_TRACEABILITY.md`](../traceability/RELEASE_TRACEABILITY.md)

Use one copy of this checklist for each RC, Beta or Stable decision. Record the exact commit, workflow runs, artifact hashes, owners and exceptions. An unchecked blocking item means **do not publish**.

## 0. Decision record

- [ ] Release type is identified: RC / Public Beta / Stable / security fix.
- [ ] Release version and target tag are recorded.
- [ ] Exact source commit SHA is recorded and frozen.
- [ ] Release coordinator and approver are identified.
- [ ] Decision date and evidence directory are recorded.
- [ ] The applicable Gate is stated: G3 RC, final Beta verification, G4, or G5.
- [ ] This checklist does not claim a Gate passed without `docs/testing/evidence/GATE-G<N>.md`.

## 1. Scope and traceability

- [ ] Every included change has a Work ID and merged PR.
- [ ] Requirement → Test → Issue → PR → Commit → Evidence links are complete.
- [ ] No unresolved P0 exists.
- [ ] Public Beta has no unresolved P1 unless the release plan permits a documented, time-bounded waiver.
- [ ] Stable has no unresolved P1.
- [ ] Known failures have owner, severity, reproduction and next action.
- [ ] No unrelated feature or Innovation was added to the stabilization release.

## 2. Branch and repository governance

- [ ] `develop` is the default integration branch.
- [ ] Release PRs target `master` only after G3 RC evidence passes.
- [ ] `develop` and `master` prohibit force push and deletion.
- [ ] Required Pull Request rules are active.
- [ ] Required CI contexts match the workflow's reported check names.
- [ ] No emergency bypass was used, or its reason, scope and follow-up review are documented.
- [ ] The release commit is reachable from the reviewed PR history.

## 3. Version and identity

- [ ] Python version, plugin manifest version, Git tag and release title follow `docs/decisions/VERSIONING.md`.
- [ ] Beta mapping is consistent: `3.0.0bN` ↔ `3.0.0-beta.N` ↔ `v3.0.0-beta.N`.
- [ ] Stable mapping is consistent: `3.0.0` ↔ `v3.0.0`.
- [ ] Changelog contains the exact version and release date.
- [ ] `/version`, package metadata and installed CLI report the expected identity.
- [ ] No existing tag or artifact will be moved, overwritten or reused.

## 4. Required test evidence

- [ ] Python 3.10 Required Check passed.
- [ ] Python 3.11 Required Check passed.
- [ ] Python 3.12 Required Check passed.
- [ ] `test-fast` passed with counts recorded.
- [ ] `test-integration` passed with counts recorded.
- [ ] `test-release` passed for this exact source/artifact identity.
- [ ] Failed = 0.
- [ ] Error = 0.
- [ ] XPASS = 0.
- [ ] Public Beta/Stable XFAIL = 0.
- [ ] Skips are zero or individually justified as non-blocking by the plan.
- [ ] JUnit and relevant logs are retained as release evidence.

## 5. Artifact reproducibility

- [ ] wheel and sdist are built from a clean checkout, frozen commit or authorized RC tag.
- [ ] Build runs outside the maintainer's mutable development environment.
- [ ] wheel contents include all required packages, manifests and resources.
- [ ] Installed artifact works outside the repository directory.
- [ ] `SHA256SUMS` covers every published artifact.
- [ ] SBOM is generated and references the exact commit/version.
- [ ] Artifact attestation/provenance is generated by the release workflow.
- [ ] Release Notes and Known Limitations reference the exact artifact set.
- [ ] Artifact filenames, hashes and metadata are mutually consistent.

## 6. Installation and lifecycle

- [ ] Clean temporary HOME install passed from the final artifact.
- [ ] `deepseek-harness install --dry-run` caused no persistent change.
- [ ] Clean install completed without source-tree imports or symlinks.
- [ ] Repeated install remained idempotent.
- [ ] `doctor` human output passed.
- [ ] `doctor --json` produced one valid JSON object with no secrets.
- [ ] Server start/status/stop/restart lifecycle passed.
- [ ] Ordinary uninstall preserved the Python distribution and user data.
- [ ] `--purge-data --confirm` deleted only allowed normalized paths.
- [ ] Explicit `python -m pip uninstall oh-my-deepseek-harness` passed after product uninstall.

## 7. Tool, context and data integrity

- [ ] Public Tool target count and names match the authoritative contract.
- [ ] Runtime Tool count matches the release's implemented state.
- [ ] Tool schemas, handlers, descriptions and API models are consistent.
- [ ] All legal Tool payloads use the unified response envelope.
- [ ] Context invariants pass: no loss, duplication, mutation or broken Tool pairs.
- [ ] Summary failures return original messages.
- [ ] Session policy and mutable state are isolated.
- [ ] Plan DAG, Memory deduplication and Checkpoint ownership/numbering invariants pass.
- [ ] Migration and rollback tests preserve Config, DB, JSONL and runtime state.

## 8. Security and privacy

- [ ] GitHub Private Vulnerability Reporting is enabled and verified from a non-maintainer view.
- [ ] Public Issue Forms route security reports to the private advisory channel.
- [ ] Open private advisories were reviewed for release impact.
- [ ] Secret scanning and dependency vulnerability results were reviewed.
- [ ] No unwaived High/Critical dependency issue remains.
- [ ] Dependency licenses are compatible with the release.
- [ ] Default server bind is loopback.
- [ ] Summary/external data transfer is disabled by default and requires informed opt-in.
- [ ] Outbound content is minimized and redacted; Tool arguments are not sent by default.
- [ ] Logs, errors, JUnit and artifacts contain no secrets or unredacted user content.
- [ ] Product directories/files use the required permissions.
- [ ] Destructive operations require confirmation and resist path traversal/symlink escape.
- [ ] Security fixes have regression tests and coordinated disclosure decisions.

## 9. Compatibility

- [ ] Supported OS matrix is tested: Linux and macOS.
- [ ] Supported Python matrix is tested: 3.10–3.12.
- [ ] Exactly the selected Hermes release/source is recorded.
- [ ] Plugin Hook, Context Engine and Tool registration probes pass against real Hermes.
- [ ] Unsupported environments are rejected or clearly marked Experimental.
- [ ] No README badge or statement expands support beyond evidence.

## 10. Migration, backup and rollback

- [ ] Upgrade fixture begins from the documented review baseline or previous published version.
- [ ] Pre-migration backup is complete and restorable.
- [ ] Config migration passed.
- [ ] DB migration passed.
- [ ] Event/JSONL migration passed.
- [ ] Old process shutdown prevents a dual-server state.
- [ ] Failure injection at each migration stage restores the previous working version.
- [ ] Unsupported downgrade is rejected before data changes.
- [ ] Manual recovery instructions are tested and included where rollback can be incomplete.

## 11. Documentation truthfulness

- [ ] README and README_EN describe the current artifact, not a future target as implemented.
- [ ] Installation, upgrade, doctor and uninstall commands were copied from verified runs.
- [ ] Tool counts and current/target distinctions are correct.
- [ ] Security/privacy defaults match code and tests.
- [ ] Supported Python/OS/Hermes claims match compatibility evidence.
- [ ] Known Limitations includes every accepted release waiver and material constraint.
- [ ] CONTRIBUTING, SECURITY, Issue Forms and PR template links resolve.
- [ ] Changelog preserves historical entries and records the new release accurately.

## 12. RC and final-tag flow

### G3 RC

- [ ] G3 evidence passed on a frozen commit SHA or disposable RC tag.
- [ ] RC tag, when used, is not a public installation entry point.
- [ ] No GitHub Release or PyPI upload was created from the disposable RC tag.
- [ ] RC artifacts and test evidence are retained for comparison.

### Final Beta verification

- [ ] G3-passed `develop` was merged to `master` through an authorized Release PR.
- [ ] Final artifacts were rebuilt from the exact `master` commit.
- [ ] Final `test-release` passed on those rebuilt artifacts.
- [ ] Final hashes, SBOM, provenance and notes reference the same commit.
- [ ] `BETA-001` is authorized to create the immutable tag and GitHub Release.

## 13. Publishing

- [ ] GitHub Release title, tag, commit and artifacts are consistent.
- [ ] Release Notes include install/upgrade/rollback and Known Limitations.
- [ ] PyPI project ownership and maintainer access were verified by `REL-005`.
- [ ] PyPI Trusted Publisher is configured and uses least privilege, if PyPI is enabled.
- [ ] No long-lived publishing token is stored in repository files or logs.
- [ ] A smoke installation from the public channel succeeds after publication.
- [ ] Published artifact hashes match pre-publication evidence.

## 14. Rollback decision

- [ ] Rollback trigger thresholds are stated.
- [ ] Rollback owner and communication channel are stated.
- [ ] Published tags/artifacts will remain immutable.
- [ ] A failed unpublished RC can be deleted without affecting public users.
- [ ] A published Beta defect results in a new prerelease version, not an overwritten artifact.
- [ ] P0 response pauses promotion and opens a private advisory plus a redacted Work ID.

## 15. Post-release monitoring

- [ ] Install, Tool, Context and migration feedback channels are monitored.
- [ ] Beta failure ledger contains environment, reproduction, severity, owner and next action.
- [ ] Every code-requiring failure has a separate Issue/Work ID.
- [ ] Affected Gates are rerun after fixes.
- [ ] Public Beta exposure metrics are recorded without uploading private telemetry by default.
- [ ] G4/G5 decisions use accumulated evidence rather than release age alone.
